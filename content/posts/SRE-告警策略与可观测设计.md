# SRE 落地：告警策略与可观测设计

> **背景：** 公司在向 SRE 文化转型，要求所有核心系统都要有明确的 SLI/SLO 与告警分级，下面是当时的完整记录与思考。

1.告警策略包括告警抑制，告警级别的区分，只让关键的指标发送告警。只有这个指标直接的指向了明确的问题，才应该发告警，比如最基础的，磁盘使用率超过90%，这是一个非常危险的指标，会直接导致后续写入都有问题，并且磁盘使用率如果没有清理策略的话，一定会持续增长而不会下降，必须立即告警。划分P0-p3级别 ，p0是直接影响到用户的级别，比如错误比例到达5%，用户会有明显的感知到系统有问题，P1是用户感知不明显但是接近了SLI的设定指标，P3是预警，提前通知运维需要关注指标。

2.当前成功率 10000-150  / 10000 = 0.985 。要求是大于等于99.5，SLO达成情况是  98%，已经违反了SLO。假设每月设定的，预算消耗40%，比如每月大于等于99.5，每月失败任务就应该是995， 995 / 30  = 33
每天的预算是33
当前是 第n天，就应该是33* n  和当前已经消耗的数量进行对比。超过进行告警

3.指标是基础数据，比如cpu，内存，磁盘，io，流量这些，基本都是相对独立的，适用于具体的资源的预警，logs是辅助排查问题使用的，一般都是问题发生后，去日志查看错误原因等等，traces是全局可观测，一般是多个业务系统之间，用一个完整的链路串起来卡顿，延迟，问题都出在哪里。我在项目中是以APM为主导，一般用户关注的还是当某个问题发生时，他的完整链路是什么，问题具体出现在哪个服务，然后根据这个服务的日志或者资源，关联查看具体的原因，是资源不足，网络连接，服务器故障，中间件故障还是什么原因导致的，分析出问题的根因。日志中也会打印traceId辅助排查这一条链路产生的所有日志。

4. 确认网络指标，从库和主库的网络延迟是多少，主从延迟时间是多少，主库写入负载判断是不是主库的压力太大，从库资源使用情况，是不是从库达到资源瓶颈导致的，查询慢SQL，是不是慢SQL拖累了主从复制。
属于延迟问题，常见原因有网络延迟，大事务占用资源，主库大量并行写入，从库无法并行回放，从库性能不足。自动恢复机制是 自动检测主从延迟时间，阈值大于10s告警，大于30触发自动恢复，自动恢复包括临时摘取从库读流量，避免查询到错误数据，并且让从库的数据追赶，动态调整复制参数，当延迟小于3秒后恢复，需要人工介入的场景是，执行自动恢复之后，还是延迟，并且持续增长，或者是主库写入过高，从库回放能力不足导致的延迟，以及发生主从数据不一致，网络故障的情况需要人为干预。

5.Lag激增说明消费者处理不过来，产生了堆积，如果不处理，可以连锁导致磁盘容量不足，内存OOM，主机故障等严重问题。监控中设计 消费者队列长度增长量持续大于消费数量的时候进行预警，当消费者开始持续一段时间比如3分钟持续消费不完新增的数据时告警。以及设定队列增长量超过设定的峰值时进行预警，比如单节点消费数量最大为1w/s，现在部署了2个消费者同时消费，那当结束数量大于2w时应该预警，持续30秒应该告警。

6.网络不太熟，

7.观察渲染任务失败率，队列长度，内存使用率这些指标，使用金丝雀发布模式，将部分测试账号导流到部分资源上，对这一部分的资源里的某个节点进行模拟宕机，只影响测试账号不影响其他生产账号。按照SRE最佳时间，在预发环境应该每周一次，生产环境每季度一次。每次发布变更后都应该在1周内进行一次。

8. 第一条通报应该包含：故障模块：渲染农场，故障等级：P0，影响范围：当日全部内容发布受影响 预计恢复时间：2小时。
后续在2小时节点或更早恢复后应该发送服务恢复的通告，若未完成恢复，则需要继续通报未恢复原因及下一个预计修复时间。
故障恢复后，应该输出故障报告，包含故障现象，故障定位，解决方案，未预警原因，补偿方案，故障根因分析以及后续修复计划。

9.先要评估 单节点日处理能力是多少。比如单节点日处理能力是100。现在需要日处理5000，那就至少需要50个节点，要求单节点故障不影响整体任务，就需要预留出1个节点进行备份，要求支持滚动更新，考虑AB更新的方式需要一倍的节点，如果用金丝雀滚动更新验证，可以只需要1/3的节点，更新时宕机也需要保证没有问题，那就需要准备50 *1.3= 65个节点，一般考虑峰值冗余30% 需要65* 1.3 = 80个节点的集群。节点按机柜进行分组，分为8组，一组10个节点，故障后k8s可以自动切换到其他节点，有冗余可以保证MTTR小于5分钟，使用多主的形式规避K8S集群本身的问题，任务分发通过rocketmq队列实现，多个节点共同订阅一个topic，天然支持负载均衡，使用半提交方式，当某个节点处理失败或宕机之后，该数据视为未提交会被下一个拉起的新节点或其他消费完成的节点消费。或者使用k8s的job方式，每个任务会单独拉起一个job运行，job如果失败本身会有指数退避重试，达到上限可以触发告警。

10.MTTR反应了系统的可恢复性，MTBF反应系统的可靠性。我当前的系统MTTR大约是10分钟

11.金丝雀发布是指，发布的新版本推送给少量的用户，避免直接发布产生的大面积的问题，在SRE框架中，这种发布方式 可以有效的减少错误和错误预算的使用并可以及时的进行回退。

12.运行手册是指的故障处理的手册，每个告警，标准的处理步骤是什么，问题排查逻辑是什么，postmortem事后分析之后，才能将这一次的经验转化为Runbook。好的运行手册可以让一个刚接手系统的工程师很快的接手ON-CALL及系统运行。
