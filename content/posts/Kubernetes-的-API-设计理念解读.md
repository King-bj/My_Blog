# Kubernetes API 设计理念解读

## 背景（Situation）

项目上云后，所有服务运行在 K8s 集群中，运维与开发都需要熟悉 K8s 的基本概念和高频操作。

## 目标（Task）

梳理出团队内最常用的命令和理念，作为新人 onboarding 与日常应急的参考。

## 行动（Action）

**所有 API 应该是声明式的**。指API应该描述状态而不是描述步骤，同时隐含了API应该是名词性质的。用户描述目标状态（What），系统负责实现过程（How）。比如yaml 的模式，replicas：3 表达了希望系统始终存在3个Pod，而不是手动执行创建3个pod。声明过后，后续发生故障，网络中断，pod故障，那么conrolller会持续协调不断保证永远有3个pod在系统中运行。名词性质表示系统关注的是对象状态而不是操作动作，所以大部分api都是Pod,Deployment,Service,volume而不是 CreatePod这种，对象表达的是期望状态而不是具体的动作。

**API 对象是彼此互补而且可组合的**。 API 对象应该尽量实现"高内聚，松耦合"。

**高层 API 以操作意图为基础设计**。设计好的API应该从业务出发，而不是从技术实现进行考虑，这个理念和面向对象的方法设计好的应用系统是类似的。比如Deployment 表达的是应用部署，StatefulSet表达的是有状态应用管理，DaemonSet表达的是每节点一个实例

**低层 API 根据高层 API 的控制需要设计**。低层API存在的目的是为了支撑高层业务模型，所以设计顺序也是业务需求 -> 高层api -> 低层能力。

**尽量避免简单封装，不要有在外部 API 无法显式知道的内部隐藏的机制**。封装应该要创造新的抽象价值，而不是简单的包装或者转发，比如Deploy Application 内部会创建资源，配置网络，注册监控，配置存储，形成新的业务能力。真正有价值的是抽象出业务，让暴露给用户的是更易于理解和更关注的业务抽象而不是API包装。避免隐藏行为则表示不同的语义应该使用不同的对象，而不是在同一个API内根据不同的类型走完全不同的逻辑，行为不同就应该定义新的对象，比如deployment 和StatefulSet，就算他们在底层都是管理pod，但实际上他们是两种完全不同的行为，如果封装到一起，就会导致外部语义和内部行为不完全一致。

**API 操作复杂度与对象数量成正比**。API复杂度不能超过O(N)， 对象数量增长时，系统仍然可以正常工作，也就是API的设计要考虑到水平扩展避免O(N²)级别的算法。

**API 对象状态不能依赖于网络连接状态**。在分布式环境下，网络连接断开是经常发生的事情，因此要保证 API 对象状态能应对网络的不稳定，API 对象的状态就不能依赖于网络连接状态。

**尽量避免让操作机制依赖于全局状态，因为在分布式系统中要保证全局状态的同步是非常困难的**。不要求整个集群节点状态完全同步，通过局部观察和持续协调，不断修正错误达到最终一致性。

简单理解起来，Kubernetes不是一个执行命令的系统，而是一个基于声明式对象、通过Controller持续协调、最终收敛到目标状态的分布式控制系统。
