# 分布式事务方案选型与落地：本地消息表实践

## 背景（Situation）

跨服务的下单 → 扣库存 → 支付链路出现过几次"扣了款但没建单"的情况，根因是网络抖动导致部分服务调用失败但没有回滚其他已成功的操作。

## 目标（Task）

选型并落地一套适合我们业务量级（中等并发、可容忍秒级最终一致）的分布式事务方案。

## 行动（Action）

### 方案选型对比

| 方案 | 一致性 | 性能 | 侵入性 | 适用场景 |
|------|-------|------|-------|---------|
| **2PC（XA）** | 强一致 | 差（全局锁） | 低 | 数据库内，不跨服务 |
| **TCC** | 最终一致 | 好 | 高（需实现 try/confirm/cancel） | 对一致性要求高且可以接受侵入 |
| **SAGA** | 最终一致 | 好 | 中（需补偿逻辑） | 长事务、流程较复杂 |
| **本地消息表** | 最终一致 | 好 | 低（仅加表） | 业务量中等，秒级延迟可接受 |

我们选择**本地消息表**：业务代码侵入最小，运维简单，且能利用已有数据库的事务保证消息写入的原子性。

### 本地消息表设计

```sql
CREATE TABLE outbox_message (
    id          BIGINT       PRIMARY KEY AUTO_INCREMENT,
    topic       VARCHAR(128) NOT NULL COMMENT 'Kafka topic',
    payload     JSON         NOT NULL COMMENT '消息体',
    status      TINYINT      NOT NULL DEFAULT 0 COMMENT '0=待发送 1=已发送 2=失败',
    retry_count INT          NOT NULL DEFAULT 0,
    created_at  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    INDEX idx_status_created (status, created_at)
);
```

### 业务写入流程

在同一个本地事务里，同时写业务数据和消息表：

```java
@Transactional
public void createOrder(OrderRequest req) {
    // 1. 写业务数据
    orderMapper.insert(buildOrder(req));
    
    // 2. 写消息表（同一事务，保证原子性）
    outboxMapper.insert(OutboxMessage.of(
        "order.created",
        JSON.toJSONString(new OrderCreatedEvent(req.getOrderId()))
    ));
}
```

### 定时扫描发送

独立的后台线程定时扫描 `status=0` 的消息，发送到 Kafka：

```java
@Scheduled(fixedDelay = 1000)
public void scanAndSend() {
    List<OutboxMessage> messages = outboxMapper.findPending(100);
    for (OutboxMessage msg : messages) {
        try {
            kafkaTemplate.send(msg.getTopic(), msg.getPayload()).get(3, SECONDS);
            outboxMapper.markSent(msg.getId());
        } catch (Exception e) {
            outboxMapper.incrementRetry(msg.getId());
            log.error("Failed to send outbox message id={}", msg.getId(), e);
        }
    }
}
```

### 消费端幂等

消费方必须实现幂等：

```java
@KafkaListener(topics = "order.created")
public void handleOrderCreated(String payload) {
    OrderCreatedEvent event = JSON.parseObject(payload, OrderCreatedEvent.class);
    
    // 幂等检查：已处理则跳过
    if (inventoryService.isProcessed(event.getOrderId())) {
        return;
    }
    
    // 处理业务逻辑
    inventoryService.deduct(event.getOrderId(), event.getItems());
}
```

### 监控指标

- `outbox_pending_count`：待发送消息数，超过阈值告警
- `outbox_retry_count`：重试次数，持续增长说明 Kafka 有问题
- `outbox_max_age_seconds`：最老未发消息的年龄，超过 30s 告警

## 收获（Result）

最终采用本地消息表 + 异步对账方案，零代码侵入业务主流程，上线后再没出现过数据不一致。每日百万级消息，Kafka 宕机恢复后自动补发，数据完整性 100%。
