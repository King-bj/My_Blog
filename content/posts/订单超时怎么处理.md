# 订单超时取消怎么做？延迟队列 + 兜底扫描方案

## 背景（Situation）

电商场景下大量订单创建后并不会立刻支付，需要在 N 分钟后自动取消并归还库存。

## 目标（Task）

在不依赖额外中间件的前提下，选一个尽量简单、可扩展、对 DB 压力小的方案。

## 行动（Action）

### 方案对比

| 方案 | 优点 | 缺点 | 适用规模 |
| --- | --- | --- | --- |
| DB 轮询 | 实现最简单 | DB 压力大、延迟不可控 | 小流量 |
| Redis ZSet（按到期时间排序） | 性能高、容易实现 | 集群高可用要考虑持久化 | 中等 |
| RocketMQ / Kafka 延迟消息 | 中间件级别可靠 | 引入新组件 | 大流量 |
| 时间轮（Netty HashedWheelTimer） | 内存级别延迟 | 进程崩溃丢任务 | 单机短延迟 |

### 我们的选型：延迟队列 + 兜底扫描

- 主路径：订单创建时投递一条带 30 分钟延迟的 RocketMQ 消息，到期消费者去取消订单。
- 兜底路径：每 5 分钟扫描一次 `orders WHERE status='UNPAID' AND created_at < NOW() - 35 min`，处理漏网订单。
- 取消逻辑做幂等：基于 `order_id + status` 的乐观更新，重复处理无副作用。

### 关键代码片段

```java
public void onCreate(Order order) {
    delayMq.send("order-timeout", order.getId(),
                 Duration.ofMinutes(30));
}

@MqListener("order-timeout")
public void onTimeout(Long orderId) {
    int updated = orderMapper.cancelIfUnpaid(orderId);
    if (updated > 0) {
        inventoryService.refund(orderId);
    }
}
```

### 监控指标

- 延迟队列积压量
- 兜底扫描每次取消的订单数（理论上应为 0）
- 取消与归还库存的耗时 P99


## 收获（Result）

延迟队列覆盖正常路径，兜底扫描防止丢消息，整体取消逻辑做了幂等设计，二者覆盖率 100%；上线后再没有出现"已超时未取消"的客诉。
