# 自动化打包更新流水线落地

## 背景（Situation）

每次版本发布都要手动打包、上传、解压、重启，操作分散在多人手里，容易漏步骤。离线或半离线环境无法直接使用 Registry 推拉镜像。

## 目标（Task）

把整个流程脚本化并接入 CI，做到一键发布，发布过程可审计。

## 行动（Action）

### 分阶段构建策略

将镜像拆分为**基础镜像（base）** 和**应用镜像（app）**：

- `runner-base`：包含运行时依赖（Python、系统库），变化频率低
- `runner`：仅打包应用代码，变化频率高

这样每次发布只需传输 `runner` 镜像，`runner-base` 不变则无需重传。

### 打包流程

```shell
# Step 1：构建基础镜像（依赖变化时才需要）
docker build -t registry.example.com/runner-base:1.1.1 \
  -f DockerfileRunnerBase .

# Step 2：构建应用镜像
docker build -t registry.example.com/runner:6.4.2 \
  -f Dockerfile .

# Step 3：导出为 tar 文件用于离线传输
docker save -o runner.tar registry.example.com/runner:6.4.2
```

### 部署流程

```shell
# 将 tar 传输到目标服务器（使用 rsync 或 scp）
rsync -avz runner.tar user@<target-server>:/opt/deploy/

# 在目标服务器上加载镜像
docker load -i /opt/deploy/runner.tar

# 停止旧容器
docker stop runner-container

# 启动新容器
docker run -d \
  --name runner-container \
  -p 8084:8084 \
  -p 8888:8888 \
  registry.example.com/runner:6.4.2
```

### 自动化脚本

将以上步骤封装为 `deploy.sh`，在 Jenkins/GitLab CI 中触发：

```shell
#!/bin/bash
set -e

VERSION=$1
REGISTRY="registry.example.com"

echo "==> Building runner image: $VERSION"
docker build -t $REGISTRY/runner:$VERSION -f Dockerfile .
docker save -o runner.tar $REGISTRY/runner:$VERSION

echo "==> Deploying to target servers"
for SERVER in $(cat servers.txt); do
  rsync -avz runner.tar user@$SERVER:/opt/deploy/
  ssh user@$SERVER "
    docker load -i /opt/deploy/runner.tar
    docker stop runner-container || true
    docker run -d --name runner-container \
      --restart unless-stopped \
      -p 8084:8084 $REGISTRY/runner:$VERSION
  "
done

echo "==> Deploy complete: $VERSION"
```

## 收获（Result）

发布周期从 2 小时缩到 15 分钟，发布过程零差错运行了大半年。基础镜像分离后，90% 的发布只传输应用镜像（约 50MB vs 之前 200MB+）。
